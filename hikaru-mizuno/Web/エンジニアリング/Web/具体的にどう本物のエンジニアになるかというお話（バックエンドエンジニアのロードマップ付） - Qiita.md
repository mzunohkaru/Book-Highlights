#### Highlights & Notes

> LocalStorage概要
- 保存場所: ブラウザのローカルストレージ領域（ユーザーのデバイス上） 容量: 通常5-10MB程度 有効期限: なし（ユーザーが手動で削除するまで永続） サーバーへの送信: 自動送信されない アクセス範囲: 同一オリジン（プロトコル、ドメイン、ポートが同じ）内のみ

> Cookie概要
- 保存場所: ブラウザのCookie領域（ユーザーのデバイス上） 容量: 1つあたり4KB程度 有効期限: 設定可能（セッションCookieは ブラウザ終了時に削除） サーバーへの送信: HTTPリクエストで自動送信される アクセス範囲: ドメインとパスで制御可能

> DNSのレコード管理

> rebaseを使ったコミットの整理
- 日常的な開発フロー
1.機能開発中は気にせず細かくコミット
2.PR作成前にrebaseで整理 
3.レビュー後のフィードバック修正もfixupコミット
4.最終的にもう一度rebaseで整理 
チーム開発での注意点 
1.既にプッシュ済みのコミットはrebaseしない
2.共有ブランチでのrebaseは避ける3.フォースプッシュは慎重に（--force-with-lease推奨）

主要なオプション 
pick: そのままコミットを保持squash: 前のコミットと統合（コメント編集可能） 
fixup: 前のコミットと統合（コメントは破棄） 
edit: コミットを編集 
drop: コミットを削除

> OAuth
- 目的
第三者アプリが、ユーザーのパスワードを知ることなく、ユーザーのリソースにアクセスする仕組み

フロー例
1. 認可リクエスト 
 App → あなた: 「Googleフォトにアクセスしたいです」 
2. 認可の取得 
 あなた → Google: 「Appがフォトにアクセスすることを許可します」 
3. 認可コードの発行 
 Google → App: 「認可コード: ABC123」 
4. アクセストークンの取得 
App → Google: 「認可コード: ABC123 と 秘密鍵で交換してください」 
Google → App: 「アクセストークン: XYZ789」 
5. リソースアクセス 
 App → Google Photos: 「トークン: XYZ789 で写真を取得」 
Google Photos → App: 「写真データを送信」

認可フロー種類 
1. Authorization Code Flow（最も一般的） 
2. Implicit Flow（非推奨）
3. PKCE（Proof Key for Code Exchange）

> OpenIDConnect
- OAuth 2.0 の上位プロトコル
目的
認証（ユーザーが誰かを確認）+ 認可（何ができるかを確認）
追加要素: IDトークン（JWT形式）
OAuthは認可のみ
OIDCは認証＋認可
トークンの適切な管理
✅ 良い例
- HTTPOnly Cookieでトークンを保存
- 短い有効期限
- リフレッシュトークンの適切な管理 ❌ 悪い例
- LocalStorageにアクセストークンを保存（XSS攻撃の危険）
- 長すぎる有効期限
- クライアントサイドでの秘密鍵管理

> DDoS
- 複数のソースから大量のリクエストを送信してサービスを停止させる攻撃
対策のポイント 

レート制限: IPアドレス単位でのリクエスト数制限 
CDN活用: 静的コンテンツの配信負荷分散 
オートスケーリング: 負荷に応じたサーバー増減 
WAF導入: 異常なトラフィックパターンの検知とブロック

> ブルートフォース
- パスワードや認証情報を総当たりで試行する攻撃

対策のポイント 
 アカウントロックアウト: 失敗回数に応じた一時的なアカウント停止 
段階的遅延: 失敗するたびにレスポンス時間を長くする 
CAPTCHA導入: 自動化攻撃の防止 
二要素認証: パスワードだけでは突破できない仕組み

> レインボーテーブル
- よく使われるパスワードのハッシュ値を事前計算して表にしたもの（レインボーテーブル）を使い、漏洩したハッシュ値からパスワードを逆算する攻撃

対策のポイント ソルトの追加: パスワードに一意な文字列を付加してハッシュ化 適切なハッシュ関数: bcrypt、scrypt、Argon2など計算コストが高いもの ストレッチング: ハッシュ化を複数回繰り返す

> パスワードリスト
- 他のサービスから漏洩したメールアドレスとパスワードの組み合わせを使って、複数のサービスで同じ認証情報を試す攻撃

対策のポイント 
異常ログイン検知: 地理的な場所、デバイス、時間帯の変化を監視 
二要素認証の強制: 特に管理者アカウント 
パスワードポリシー: 他サービスとの差別化を促す ログイン通知: 成功・失敗両方の通知

> XSS
- ユーザーの入力をそのまま画面に表示する際、悪意のあるJavaScriptコードを埋め込んで他のユーザーのブラウザで実行させる攻撃

対策のポイント 
入力値検証: ホワイトリスト方式での厳格なチェック 
出力エスケープ: HTML特殊文字の無害化 
CSP導入: Content Security Policyでスクリプト実行を制限 
HttpOnlyクッキー: JavaScriptからのアクセスを防止 

 反射型、格納型、DOM型の3種類があり、それぞれ対策ポイントが異なります。フロントエンド・バックエンド両方での対策が必要です。

> CSRF
- ユーザーが認証済みのサイトに対して、攻撃者が用意した別サイトから意図しないリクエストを送信させる攻撃

対策のポイント 
CSRFトークン: フォームに一意なトークンを埋め込み、サーバー側で検証 
SameSite属性: クッキーのクロスサイト送信を制限 
Refererチェック: リクエスト元URLの検証 
重要操作の再認証: パスワード入力やワンタイムパスワード

> リトライ設計
- 「一時的な障害は必ず発生する」という前提

リトライ戦略の種類 
 固定間隔リトライ 
 1秒後 → 1秒後 → 1秒後 
 線形バックオフ 
 1秒後 → 2秒後 → 3秒後 → 4秒後 指数バックオフ（最も一般的） 
 1秒後 → 2秒後 → 4秒後 → 8秒後 → 16秒後 


エラー分類とリトライ判定 

リトライすべきエラー 
 一時的なエラー 
-HTTP 5xx系エラー（500, 502, 503, 504） 
 ネットワークタイムアウト 
-接続拒否（Connection Refused） 
-DNS解決失敗 
判断基準: 時間を置けば成功する可能性があるエラー 

リトライすべきでないエラー 
恒久的なエラー 
-HTTP 4xx系エラー（400, 401, 403, 404） 
-データフォーマットエラー 
-認証・認可エラー 
-ビジネスロジックエラー 
判断基準: リトライしても同じ結果になることが確実なエラー
