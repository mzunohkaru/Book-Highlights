# Vue.js/Nuxt.js テスト設計思想ガイド

## はじめに

このガイドでは、Vue.js/Nuxt.js アプリケーションにおけるテスト設計の思想と実践的なアプローチを解説します。テストは単なる品質保証のツールではなく、設計を改善し、開発速度を向上させる重要な開発プラクティスです。

### テストピラミッドとは

```
        /\
       /  \  E2E Tests (少数)
      /____\
     /      \
    / Integration \ Integration Tests (中程度)
   /____________\
  /              \
 /  Unit Tests    \ Unit Tests (多数)
/__________________\
```

**なぜピラミッド型なのか？**

- **Unit Tests**: 高速、安定、デバッグしやすい
- **Integration Tests**: 実際の連携を検証、適度な実行時間
- **E2E Tests**: ユーザー体験を検証、実行が重く不安定になりがち

## コンポーネントテスト

### 基本方針

コンポーネントテストでは「**ブラックボックステスト**」の考え方を採用します。つまり、内部実装ではなく外部仕様（入力と出力）に注目します。

```typescript
// ❌ 悪い例: 内部実装をテスト
test("内部のdataプロパティが変更される", () => {
  const wrapper = mount(Counter);
  wrapper.vm.internalCount = 5; // 内部実装に依存
  expect(wrapper.vm.internalCount).toBe(5);
});

// ✅ 良い例: 振る舞いをテスト
test("ボタンクリック時にカウンターが増加する", async () => {
  const wrapper = mount(Counter);
  await wrapper.find('[data-testid="increment-btn"]').trigger("click");
  expect(wrapper.text()).toContain("1");
});
```

### Props・Emits 関連

**なぜ Props・Emits のテストが重要か？**

コンポーネントの「契約」を定義する部分だからです。この契約が守られることで、親子コンポーネント間の連携が保証されます。

```typescript
// props検証の実例
describe("UserCard component", () => {
  test("必須propsが未指定時にwarningが出力される", () => {
    const spy = vi.spyOn(console, "warn").mockImplementation(() => {});
    mount(UserCard); // nameプロパティが必須だが未指定
    expect(spy).toHaveBeenCalledWith(
      expect.stringContaining("Missing required prop")
    );
    spy.mockRestore();
  });

  test("emitが適切なペイロードで発火する", async () => {
    const wrapper = mount(UserCard, {
      props: { user: mockUser },
    });

    await wrapper.find('[data-testid="edit-btn"]').trigger("click");

    expect(wrapper.emitted("edit")).toBeTruthy();
    expect(wrapper.emitted("edit")[0]).toEqual([mockUser.id]);
  });
});
```

**ベストプラクティス:**

- テストデータはファクトリーパターンで作成
- 境界値（空文字、null、undefined）を含めてテスト
- TypeScript の型チェックに頼らず、実行時の検証も実装

## Composables テスト

### テスト対象の選び方

Composables は**ピュアなロジック**を含むため、単体テストに最適です。

```typescript
// useCounter.test.ts
import { useCounter } from "~/composables/useCounter";

describe("useCounter", () => {
  test("初期値が正しく設定される", () => {
    const { count } = useCounter(5);
    expect(count.value).toBe(5);
  });

  test("increment関数でカウントが増加する", () => {
    const { count, increment } = useCounter(0);
    increment();
    expect(count.value).toBe(1);
  });

  test("computed値が状態変更に追従する", () => {
    const { count, increment, isEven } = useCounter(0);
    expect(isEven.value).toBe(true);

    increment();
    expect(isEven.value).toBe(false);
  });
});
```

### API 通信のテスト戦略

**モックの使い分け**

```typescript
// $fetchをモックする例
describe("useApi", () => {
  beforeEach(() => {
    // 各テストで独立したモックを作成
    vi.clearAllMocks();
  });

  test("成功時のレスポンス処理", async () => {
    const mockData = { id: 1, name: "Test User" };
    const mockFetch = vi.fn().mockResolvedValue(mockData);

    // $fetchをモック
    vi.stubGlobal("$fetch", mockFetch);

    const { fetchUser, data, isLoading } = useApi();

    expect(isLoading.value).toBe(false);

    await fetchUser(1);

    expect(mockFetch).toHaveBeenCalledWith("/api/users/1");
    expect(data.value).toEqual(mockData);
    expect(isLoading.value).toBe(false);
  });

  test("エラー時の処理", async () => {
    const mockError = new Error("Network Error");
    const mockFetch = vi.fn().mockRejectedValue(mockError);

    vi.stubGlobal("$fetch", mockFetch);

    const { fetchUser, error, isLoading } = useApi();

    await fetchUser(1);

    expect(error.value).toBe(mockError);
    expect(isLoading.value).toBe(false);
  });
});
```

## Store/Pinia テスト

### 状態管理テストの原則

1. **アクションのテスト**: 副作用と状態変更を分離して検証
2. **ゲッターのテスト**: 純粋関数として扱う
3. **初期状態のテスト**: 予期しない初期値を防ぐ

```typescript
// userStore.test.ts
describe("userStore", () => {
  let store: ReturnType<typeof useUserStore>;

  beforeEach(() => {
    setActivePinia(createPinia());
    store = useUserStore();
  });

  test("初期状態が正しく設定される", () => {
    expect(store.users).toEqual([]);
    expect(store.isLoading).toBe(false);
    expect(store.error).toBeNull();
  });

  test("fetchUsers アクションが状態を正しく更新する", async () => {
    const mockUsers = [{ id: 1, name: "User 1" }];
    vi.mocked($fetch).mockResolvedValue(mockUsers);

    await store.fetchUsers();

    expect(store.users).toEqual(mockUsers);
    expect(store.isLoading).toBe(false);
  });

  test("activeUsers ゲッターが正しく計算される", () => {
    store.$patch({
      users: [
        { id: 1, name: "Active User", isActive: true },
        { id: 2, name: "Inactive User", isActive: false },
      ],
    });

    expect(store.activeUsers).toHaveLength(1);
    expect(store.activeUsers[0].name).toBe("Active User");
  });
});
```

## 高度なテスト手法

### テスト駆動開発（TDD）サイクル

```
Red → Green → Refactor
🔴    🟢     🔵
```

**実践例:**

```typescript
// 1. Red: まずテストを書く（失敗する）
test("税込価格を計算できる", () => {
  expect(calculateTaxIncluded(100, 0.1)).toBe(110);
});

// 2. Green: テストが通る最低限の実装
function calculateTaxIncluded(price: number, taxRate: number): number {
  return price + price * taxRate;
}

// 3. Refactor: コードを改善
function calculateTaxIncluded(price: number, taxRate: number): number {
  if (price < 0 || taxRate < 0) {
    throw new Error("価格と税率は負の値にできません");
  }
  return Math.round(price * (1 + taxRate));
}
```

## テストの基本的な考え方

### 何をテストするか

**外部仕様（パブリック API）**

- コンポーネントの props → 表示内容
- ユーザーの操作 → イベント発火、状態変更
- API レスポンス → UI の変化

**テスト可能な設計**

```typescript
// ❌ テストしにくい設計
export default defineComponent({
  setup() {
    const handleClick = () => {
      // 複雑なロジックが直接書かれている
      if (
        user.value.role === "admin" &&
        user.value.permissions.includes("write")
      ) {
        showModal.value = true;
        analyticsTracker.track("admin_action");
        localStorage.setItem("lastAction", Date.now().toString());
      }
    };

    return { handleClick };
  },
});

// ✅ テストしやすい設計
export default defineComponent({
  setup() {
    const { canPerformAction } = usePermissions();
    const { track } = useAnalytics();
    const { saveLastAction } = useLocalStorage();

    const handleClick = () => {
      if (canPerformAction("write")) {
        showModal.value = true;
        track("admin_action");
        saveLastAction();
      }
    };

    return { handleClick };
  },
});
```

### 何をテストしないか

**内部実装の詳細**

- private メソッドの内部ロジック
- コンポーネントの内部状態（data, ref）
- 算出プロパティの計算過程

**フレームワークの機能**

- Vue.js の響応性システム
- ルーターの基本機能
- 外部ライブラリの動作

### テストの保守性

**良いテストの特徴**

1. **Independent（独立性）**: 他のテストの実行結果に依存しない
2. **Repeatable（再現性）**: 何度実行しても同じ結果
3. **Self-validating（自己検証）**: 成功/失敗が明確
4. **Timely（適時性）**: 機能実装と同時に書く
5. **Fast（高速）**: 素早くフィードバックを得られる

```typescript
// ❌ 悪い例: テスト間で状態を共有
describe("UserService", () => {
  let users: User[] = [];

  test("ユーザーを追加", () => {
    users.push(createUser());
    expect(users).toHaveLength(1);
  });

  test("ユーザーを削除", () => {
    // 前のテストの結果に依存している
    users.pop();
    expect(users).toHaveLength(0);
  });
});

// ✅ 良い例: 各テストが独立
describe("UserService", () => {
  test("ユーザーを追加", () => {
    const service = new UserService();
    service.addUser(createUser());
    expect(service.getUsers()).toHaveLength(1);
  });

  test("ユーザーを削除", () => {
    const service = new UserService();
    const user = createUser();
    service.addUser(user);
    service.removeUser(user.id);
    expect(service.getUsers()).toHaveLength(0);
  });
});
```

## まとめ

効果的なテストは以下の価値を提供します：

1. **品質保証**: バグの早期発見と回帰防止
2. **設計改善**: テストしやすい設計は良い設計
3. **開発速度向上**: 安心してリファクタリングできる
4. **ドキュメンテーション**: テストは生きた仕様書
5. **チーム協働**: 共通理解の基盤

テストは「書く」ことよりも「設計」することが重要です。何をどのようにテストするかを明確にし、保守可能で価値のあるテストスイートを構築していきましょう。
