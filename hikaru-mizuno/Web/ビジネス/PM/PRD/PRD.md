# プロダクトドキュメンテーション
1. Product Vision
    - プロダクトを作る目的は？
    - なぜ我々が作るのか？
    -  なぜユーザーにそのプロダクトが必要なのか？
    -  プロダクトがあるとないとで世界がどのように変わるのか？
2. Product Strategy
    - プロダクトを実現するために、「何をして」「何をしないか」
3. Product Roadmap
    - どのような順番でプロダクトを作っていくか？
4. Product Concept
    - これから作り上げるプロダクトの姿とは？
5. PRD
    - 単位期間で何を作るのか？

⚠️ Vision, Strategy, Concept, Roadmapはステークホルダーと同意できるまで往復する
	PRDを書くためには、これら上位の意思決定やドキュメント化が終わっている必要がある


## Product Vision
目的
- プロダクトの「なぜ」に対するメッセージ（ビジョンステートメント）
- プロダクトに関わる人を引きつける、同じ方向を向いてもらう
- 全ての意思決定はこのビジョン実現のためにある
- 必ずしもユーザーに対して謳う必要はない

**プロダクトビジョンにそぐわないPRDは書くべきではない**

![](Product%20Visionのスコープ.png)
アーリーステージスタートアップの場合、Product VisonとCompany Visionは一致している場合が多い
そこから導出されるProduct Strategyやロードマップも会社で一意

規模が大きくなると各プロダクトグループごとにProduct Visionを用意するが、==必ずCompanyレベルと整合性は取る==


## Product Strategy
- Product Visionを達成するためにクリアすべき仮説
	- Visionは基本的に不変だが、マーケットや競合の状況において、Strategyは変わる

最低でも深める議論点  
- ターゲットユーザーは？
- ユーザーのペインポイントをどう解決するのか？
- どのようなプロダクトでどこで差別化できるか？
- ビジネス上求められるゴールは？

最終的に以下を明らかにする  
- コスト構造と収益獲得方法
- 競合を誰とするか？（同一業界だけに競合が存在するわけではない）
- チャネル（どのようにプロダクトを広めていくか、手にしてもらうか？）

## Product Roadmap
Product Strategyを絵に描いた餅に終わらせないための重要なステップ

- ロードマップは基本ハイレベルな情報に止める
	- 市場により変化するため、四半期ごとに見直す
- エグゼクティブチームがインベスターにプレゼンするときにも使われる
- Product Strategyから３つの観点でポテンシャルがあるテーマを抽出する
    - Delight Customer（ユーザーがどれだけ喜んでくれそうか）
    - Margin Enhancement（どれだけ利益率が向上するか）
    - Hard to copy by competitor（作ることで、どれだけ競合への参入障壁を築くことができるか）

## Product Concept
- 特定の機能やプロダクトの最終形態（ゴール）を表現する
	- ビジュアルがあればなお良い
- 開発前に、ステークホルダーやプロダクトチームに理解しておいてほしいこと、同意した項目、制約条件などを洗い出しておく

### Product Inception Deck

- 我々はなぜここにいるのか？
- エレベータピッチ
    - 10秒でプロダクトを説明できる
        - [潜在的なニーズや課題を解決]したい
        - [対象顧客]向けの、
        - [プロダクト名]というプロダクトは
        - [プロダクトのカテゴリー]です。
        - これは[重要な利点、対価に見合う価値]ができ、
        - [代替手段の最右翼]とは違って、
        - [差別化の決定的な特徴]が備わっている
- プロダクトデザイン（ビジュアル）
- やらないことリスト
- ステークホルダー
- 解決案
- 夜も眠れない問題
	- 考えられるリスク
	- リスクへの対処法
- 期間を見極める
	- 3ヶ月,6ヶ月,1年など
- 何を諦めるのか
    - スコープ、期間、予算、品質の中でどんなトレードオフを受け入れるか？
        - 例）
            - 予算がかかっても、品質が高いものをリリースする
            - 期間が伸びても、スコープは変えずにリリースする
- 何がどれだけ必要か
    - チーム、予算


## CPCC  
自社プロダクトが置かれている環境を<u>市場や競合と比較する</u>ことで立ち位置を把握し、新たなプロダクト開発の機会や成長戦略、ピボットを考える方法

Customer
- 顧客
- 過去のデータから現在に至るまでのトレンド（上昇傾向、下降傾向、定常的）
- 各セグメントが価値を感じているもの
- 価格反応度
- コミュニケーションチャネル（セグメントごと）
- カスタマーのボリューム

Product
- プロダクト名
- プロダクトができること
- プロダクトの使われ方
- 競合のプロダクトを買う理由
- コモディティ化 or 差別化
- 競合に真似されるプロダクトの箇所
- 別のセグメントに代理プロダクトが存在する可能性
- 競合は、新規参入 or 古参
- 単一プロダクト or ソリューションパッケージ

Company
- 自社の強み
    - コア競争力
- 販売チャネル
- コスト構造
- ブランド
- 財務状況
- 組織体制
- 法規制環境

Competition
- マーケット集中度
    - 独占、寡占、混沌、競合のマーケットの有無とサイズ
- 競合
    - 展開しているプロダクト
    - 最近の打ち手
    - 戦略・戦術
        - 我々がしていないこと + していない理由
    - 販売チャネル
    - 参入障壁の有無とサイズ

# 仮説  
仮説を立てる
- 1PRD = 1つの仮説
	- ⚠️ スコープは大きくしない
	    - 複数の仮説を立ててしまうと、検証テストが複雑になる

仮説を研ぎ澄ます
- Conclusiveness Test
	- 筋の良い仮説かどうか確かめるテスト
		- 「もしXという仮説が確かなら、プロダクトYにZという機能を乗せるべき」
            - 視点を変えた仮説：「もしXという仮説が確かであっても、プロダクトYにZという機能を乗せるべきではない」
	            - ↑この論をサポートするだけの仮説や事実はあるか？
            - 視点を変えた仮説：「もしXという仮説が不確かであっても、プロダクトYにZという機能を乗せるべき」
	            - ↑この論をサポートするだけの仮説や事実はあるか？
        - `目立った反証が導かれなければOK`
- Backward Casting
	- この施策が「既に」成功していたとしたら、何が成功要因か？
		- <u>視点を未来に置く</u>
	    - 出てきた要因から、センターピンを探す

# Whatを定義する
What = プロダクトを多面的に捉えて言語化すること

![](Whatを定義.png)
### 特性で考える
- 機能
- デザイン
- API
- セキュリティー・プライバシー
- 外部依存性


### 時間 x 価値軸で考える  
- Phase 1
    - MVPフェーズ
    - UIUXで荒めなところがあってもコアとなる価値を体験できる
- Phase 2
    - MVPフェーズで対応しきれていないもの
    - Phase 1の反応を見て、随時プランは更新になることが多い
- Phase 3
    - やろうとしていた昨日はほぼ網羅

→Phase 1のPRDの場合は、Phase2,3は見通しを説明するのに留める


### ビジネス要件


| 考える項目              | 内容                                                                    |
| ------------------ | --------------------------------------------------------------------- |
| ゴール                | プロダクトや機能のゴール<br>例）<br>・これくらいのエンゲージメント発生を目指す<br>・これくらいのMAUを目指す         |
| 提案サマリー             | ・ゴールの肉付けという立ち位置<br>・一言で言えば何をする機能・プロダクトか<br>・どんなユーザーに対して、どのような便益があるのか？ |
| SoW（Scope of Work） | ・何を作り、何を作らないか？<br>・作るものと作らないものの境界線をクリアにする                             |
| リスク                | ・プロダクト施策を進めるにあたり、何がリスクとなるか？<br>・その場合どのようにリスクを最小化できるか？                 |
| 依存関係               | 社内・社外で依存関係となる部分はどこか？                                                  |

### プロジェクト要件


| 考える項目  | 内容                                                                        |
| ------ | ------------------------------------------------------------------------- |
| スケジュール | PMとしてリリースしたいタイミングはいつか？                                                    |
| フェーズ   | ・今回のプラダクト試作は単発か？それとも将来フェーズがあるのか？<br>・その場合どのように施策を分けるのか？またそれはなぜそのように分けるのか？ |
| テストプラン | 機能・プロダクトの受け入れレベルをどこに置くか？                                                  |
| メンバー   | チームメンバーはどこから何名必要か？                                                        |


### デザイン要件  

- 最低でもワイヤーフレーム Low Fi なデザインモックアップは用意する

- ユーザーのモチベーションを捉えている

## PRDを読む人が考えること

PM
- ユーザーへの価値は体現できているか？
- 何か助けられるところがあるか？
- 抜け漏れ、矛盾はないか？
- スコープは適切か？

エンジニア  
- ユーザーにとって意味はありそうか？
- 技術的なスコープの広さは？
- 既存プロダクトとの整合性や新規性、時間軸は？
- 他チームとの協業は必要か？

デザイナー  
- ユーザーが感じている問題を理解できているか？
- UIUXの観点で直感的で使いやすいデザインになっているか？

データサイエンティスト  
- どのようなデータを使って仮説を組み立てているか？
- 仮説の組み立ては、論理的破綻していないか？
- プロダクトの成功の確度を上げるためにどんなデータがあればいいか？

マーケティング  
- ターゲットユーザーは明確化？
- ターゲットにどのようなメッセージを出すとプロダクトを使ってもらえそうか？

CS  
- ユーザーが問題に直面した時、どんな解決策を用意できそうか？

法務  
- PRDに記載されていることで約款や箒に接触するリスクはあるか？
- 特許を取れそうなアイデアか？

セールス  
- どのようにプロダクトを売っていくか？
- 営業として使える事実やデータは何か？
- 他者との連携によりさらに価値を増大できないか？

	ゴールまでのパスが綺麗に描ける


## カスタマージャーニーマップ
- 時系列で示すユーザー（ペルソナ）の行動とその感情の移り変わり
- プロダクトの体験をEnd to Endで表すパターン
- 特定の機能部分で切り出し、タスクを完了するまでを表現するパターン
- どのようなタイミングやプロセスでペルソナの感情がプラスやマイナスに触れそうかを可視化できる
- どの部分の体験をよくすることが価値につながるか、その可能性が見えやすくなる

フォーマット

|              | step 1 | step 2 | ... | step X |
| ------------ | ------ | ------ | --- | ------ |
| ペルソナの考え・感情   |        |        |     |        |
| ペルソナの行動      |        |        |     |        |
| ペルソナのタッチポイント |        |        |     |        |
| ペルソナのペインポイント |        |        |     |        |
| 変えるべきこと      |        |        |     |        |


カスタマージャーニーマップの種類
- Current State Map（現状の体験, As-Is）
- Future State Map（理想的な体験, To-Be）
- Day in the life（1日の時間の中におけるプロダクト体験）
- Buyer's journey map（購入意思決定者の体験）

PRDを書くスキルの磨き方
- カスタマージャーニーを考えながら日常の行動を観察してみる
- ユーザーとしてストレスがかかる部分はどこか？
	- ストレスがかかるのはなぜか？
- もし〜したら？（What if）、〜できるとしたらどうなるか？（How might we〜？）で考える（短期的・長期的）
