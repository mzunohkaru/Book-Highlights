## MCPとは

### MCPの定義

Model Context Protocol (MCP) は、AI（LLM）とツール・データソース間の通信を標準化するオープンプロトコルです。クライアントとサーバーが共通のルールに基づいて対話することで、異なるサービスやツールを積み木のように組み合わせて利用できます。

### MCPが注目される理由

1. **トークン数の増加による処理能力の向上**
   - MCPのような「ツール仕様のカタログ」が全文渡っても破綻しない

2. **エージェント構築需要の高まり**
   - ツールを複数呼び出し、状態を保ちながら対話できるエージェント型AIが注目
   - その基盤となる「ツール連携の共通プロトコル」としてMCPが最適

3. **オープンソース化・コミュニティの成長**
   - MCPはオープンプロトコルとして公開されており、誰でもサーバーを実装可能

### 共通ルール

MCPは、初期化で互いの"立場と機能"を確認し合い、あとは統一フォーマットのリクエスト/レスポンスで自由にやり取りする仕組みです。

1. **共通言語はJSON-RPC**
   - MCPでは「JSON-RPC 2.0」が共通フォーマット

2. **最初の"名刺交換"：initialize**
   - クライアントがサーバに呼びかけるとき、まず "initialize" メソッドを送る
   - 「私はこういう機能がある」「あなたはどんな機能を提供できる？」という名刺交換

3. **チャンネルが開いたあと**
   - 一度初期化が済めば、同じルールでやり取り
     - tools（登録された関数の呼び出し）
     - resources（ファイルやデータ取得）
     - prompts（会話テンプレートの取得）
     - logging / completion / ping

4. **現在の標準トランスポート**
   - stdio（標準入出力）
   - Streamable HTTP

## MCPアーキテクチャ

### 3つの役割

MCPは「ホスト（Host）」「クライアント（Client）」「サーバ（Server）」の3つの役割で構成されます。

#### 1. ホスト (Host)

ホストはMCP全体の中枢となる存在です。

**役割:**
- 複数のクライアント（セッション）を生成し管理
  - サーバごとに必要なセッション（クライアント）を作り、セキュリティや権限を統括
- AI（LLM）との連携・指揮
  - AIモデルにどのようなデータや機能を活用させるかを制御
  - 必要に応じてサーバへリクエストを送るよう指示
- 複数サーバからの情報を集約し、AIに活用
  - 各クライアントが取得した情報を組み合わせて、AIが最適に利用できる形にまとめる

#### 2. クライアント (Client)

クライアントは"特定のサーバと通信するための1対1のセッション"を担当します。

**役割:**
- 1つのクライアントは1つのサーバ専用
  - 例：「DBサーバ用のクライアント」「翻訳サーバ用のクライアント」
- JSON-RPCでのやり取り
  - initialize や call_tool, read_resource などのメソッドを使用
- 通知やイベントへの対応
  - ログ通知などがサーバから届いた場合、クライアント側が受け取り、必要ならホストへフィードバック

**実装のポイント:**
- クライアントはMCPが提供する実装が比較的に少ない
- 基本的にSession（プロトコル層）と、stdio_client, sse_client, websocket_clientが用意されている
  - **低レベル層: ClientSession**
    - JSON-RPCメッセージを実際に生成し送信、サーバのレスポンスを待つ
    - initialize や tools/call などのコア操作をローレベルで扱う
  - **トランスポート**
    - 標準入出力（stdio）や SSE（HTTP経由）などを使い、JSON形式のメッセージをやり取り

#### 3. サーバ (Server)

サーバはAIが活用できる機能やデータを公開する存在です。

**役割:**
- ツールやリソースの提供
  - 例：「翻訳機能」「データベース照会機能」「ファイル読み書き」など
- ホストや他サーバの情報には直接アクセスしない
  - セキュリティを保つため、自分に与えられた権限とリソースのみを扱う
- 必要に応じたLLM活用
  - クライアント経由でホストのLLM（AI）に問い合わせることも可能

**実装のポイント:**
- サーバは比較的に色んな実装が提供されている
- 低レベルのServerと、それをラッピングしたFastMCPを用いて開発が可能
  - **低レベル層: Server**
    - @server.call_tool や @server.list_tools() などのデコレータでリクエスト種別に対応するハンドラを定義
  - **内部的な接続管理: ServerSession**
    - 新たなクライアント接続ごとにセッションを生成し、JSON-RPCメッセージを実際に受け取って処理
  - **高レベルフレームワーク**
    - FastMCP などを使えば SSE ルートやツール管理が自動セットアップされ、サーバ側の実装がシンプルに済む

### デザイン原則

1. **サーバはできるだけシンプルに**
   - 大きなオーケストレーションはホストが担う一方、サーバは必要な機能だけに特化

2. **高い組み合わせ性**
   - 共通プロトコルでつながるため、サーバを積み木のように増やしていくだけで新しいAI機能を取り込める

3. **視野を限定**
   - セキュリティ上、各サーバはあくまで自分の権限内で完結
   - サーバ同士は直接データを共有しない

4. **段階的な機能追加**
   - コア機能は最小限に留め、拡張機能は"capability negotiation（機能交渉）"で合意を取りながら追加
   - 後方互換性を保ちつつ、プロトコルを成長させられる

### MCPの独自性

- **REST APIよりも** ステートフルで双方向通信が可能
- **メッセージキューよりも** 直接的で軽量
- **WebSocketよりも** 構造化され標準化されている
- **gRPCよりも** 柔軟で理解しやすい
- **GraphQLよりも** ツール呼び出しに焦点を当てている
- **RPCよりも** リソースとコンテキストを重視している

## MCPプリミティブ

MCPは、サーバー側とクライアント側で異なるプリミティブ（基本構成要素）を提供します。

### サーバー側プリミティブ

サーバー側のプリミティブは、MCPサーバーがクライアントに対して提供する機能やデータの種類を定義します。

#### 1. Tools

Toolsは、エージェントが外部世界と対話するための主要なメカニズムです。

**特徴:**
- MCPサーバーがクライアントに提供する実行可能な機能
- 長時間実行されるツールの進捗状況を通知・更新できる
- ユーザーは処理中も進捗を把握可能

**使用例:**
- データベースへのクエリ実行
- ファイルの読み書き
- 外部APIの呼び出し

#### 2. Resources

Resourcesは、サーバーからクライアントに追加したい**任意のコンテキストを提供する**ための汎用メカニズムです。

**特徴:**
- 読み取り専用のデータを提供
- Claude.aiでは、ファイル添付と同様のものとして表現される
- ファイルの内容、データベースのレコード、APIのレスポンスなどが含まれる

**目的:**
- データ参照
- コンテキスト情報の提供

#### 3. Prompts

Promptsは、ユーザー中心のプリミティブで、エンドユーザーが会話に特定のコンテキストを追加できます。

**特徴:**
- 再利用可能なプロンプトテンプレートやワークフローを提供
- スーパーユーザー向けの機能

**使用例:**
- 特定のGitHubプルリクエストの説明を会話に追加
- 定型的なタスクのテンプレート化

**将来の見通し:**
「世界がよりエージェント的になるにつれて、これらはほとんどのユーザーにとってあまり役立たなくなると考えています。しかし、スーパーユーザーにとっては依然として非常に便利です。」

### クライアント側プリミティブ

クライアント側のプリミティブは、MCPクライアントが提供する機能を定義します。

#### 1. Sampling（サンプリング）

MCPサーバーがクライアント側のLLMに推論をリクエストできる機能です。

**特徴:**
- サーバーからクライアントのLLMへ問い合わせ可能
- エージェント的な動作を実現

#### 2. Roots（ルート）

主にローカルMCPサーバーで使用されるプリミティブです。

**用途:**
- ローカルファイルシステムのルートディレクトリの指定
- アクセス権限の管理

#### 3. Elicitation（誘導）

MCPサーバーがエンドユーザーから直接情報を要求できる機能です。

**使用例:**
- MCPサーバーが潜在的に破壊的な操作を行おうとするとき、ユーザーが望んだ操作か確認する
- ユーザーの明示的な承認が必要な処理の実行前確認

## 通信プロトコルとトランスポート

### コア要素

クライアントとサーバが話す方法は3つのコア要素で構成されます：

1. **プロトコル層（セッション）**
2. **トランスポート層**
3. **メッセージタイプ**

#### 1. プロトコル層（セッション）

- メッセージの枠組み（JSON-RPC 構造）を定義し、対応するリクエストとレスポンスを結びつける
- ServerSession / ClientSession などのクラスで、サーバとクライアントそれぞれのやり取りを管理
  - **クライアント側**: ClientSession を使い、"リクエストを作って送る/レスポンスを受け取る"
  - **サーバ側**: ServerSession を使い、"リクエストを受け取りハンドラを呼ぶ/結果を返す" フローを管理
- 送受信は「MCPメッセージ（Requests / Results / Errors / Notifications）」として扱われる

#### 2. トランスポート層

実際のバイト列を「どこで」「どう送るか」を担います。

##### stdio方式（ローカル処理）

- **利用場面**: ローカル処理
- **仕組み**: 標準入出力の文字列行をJSONとしてセッションに供給
- **特徴**:
  - 遅延: 非常に低い（ローカル）
  - 信頼性: ローカルプロセスで高い信頼性
  - 接続モデル: 1:1（クライアントとサーバープロセス）
  - デプロイの複雑さ: 低い（ローカルプロセス間通信）
  - ネットワーク転送: 非サポート（ローカルのみ）
  - セキュリティ: ローカルプロセスで安全
  - リソース消費: 低い
  - 拡張性: 限定的（単一クライアントのみサポート）

**stdio方式の動作フロー:**

```
STEP 1: ユーザー入力
「このPDFをMarkdownに変換して」
    ↓
STEP 2: MCPホスト（Claude Code等）
- ローカルで動作
    ↓ LLM API（インターネット経由）
STEP 3: LLMプロバイダー（Anthropic等）
- 入力を解析し「MCPサーバーを使え」と判断
    ↓ 指示を返す
STEP 4: MCPホスト
- MCPサーバーを起動
STEP 5: MCPサーバー（ローカル）
- PDFを読み取り、Markdownに変換
- ※この段階では外部送信なし
    ↓ 処理結果を返す
STEP 6: MCPホスト
- 結果を受け取る
    ↓ LLM API（処理結果を含む）
STEP 7: LLMプロバイダー
- 変換されたMarkdownテキストを受信
- 解析して応答を生成
```

**重要な誤解の訂正:**
- 「stdio方式ならローカル処理だから安全」という誤解が広まっていますが、これは正しくありません
- ローカルで処理された結果はLLMプロバイダーに送信されます

**実装言語:**
- npx: JavaScript/TypeScript製（例：@modelcontextprotocol/server-filesystem）
- uvx: Python製（例：markitdown-mcp）- 10倍高速

##### HTTP + SSE方式（リモート処理）

- **利用場面**: 外部サービス連携
- **仕組み**: サーバからクライアントへはSSEイベント、クライアントからサーバへはHTTP POST
- **特徴**:
  - 遅延: 比較的低いが、ネットワーク条件に左右される
  - 信頼性: 自動再接続とエラー処理メカニズムを備えている
  - 接続モデル: 多クライアント（一つのサーバーで複数クライアントを処理可能）
  - デプロイの複雑さ: 中程度（HTTPサーバーのサポートが必要）
  - ネットワーク転送: サポート（ネットワーク通信可能）
  - セキュリティ: HTTPSによりセキュリティ強化可能
  - リソース消費: 中程度（HTTP接続維持が必要）
  - 拡張性: 優れている（複数クライアント接続をサポート）

### SSE (Server-Sent Events)

#### SSEとは

- サーバー送信イベント（Server-Sent Events、SSE）は、HTTPプロトコルを使用してサーバーからクライアント（ウェブブラウザなど）へ一方的にデータをストリーム配信するための標準技術
- SSEは、サーバーからクライアントへの単方向通信を提供
- WebSocketは、サーバーとクライアント間の双方向通信を提供（比較として）

#### SSEの仕組み

- SSEはHTTPサーバー側（MCPサーバー側）が HTTP の Transfer-Encoding: chunked を使ってレスポンスすることで、サーバー側からデータを分割して送信できる仕組み
- サーバー側は任意のタイミングでクライアント側にデータを通知することができる
- クライアントとサーバーがHTTP接続を継続した状態で待機することで、サーバー側から通知が必要になったタイミングで、サーバー側からPUSH通知を送信できる

**SSEの重要な点:**
- サーバー側からPUSHすることしかできない
- 一番最初にクライアント側からリクエストを送信した以降、クライアントからの送信はできない
- クライアント側はデータを受け取るだけの状態になる

```
Client -[POST/mcp]-> Server
Client <-[  data  ]- Server
Client <-[  data  ]- Server
```

### Streamable HTTP

#### MCPの通信プロトコルとしてのSSE

- 現在はSSEはStreamable HTTPという、独自のプロトコルに置き換えられています
- SSEはStreamable HTTPで引き続き内部的に利用されています

#### Streamable HTTPとは

**基本的な考え方:**
- 普段は一般的なHTTPを使う
- MCPサーバー側からPUSH通知をしたいときはSSEを使う
- MCPサーバー側からPUSH通知を送信する要件がなければ、MCPサーバー側はSSEを実装する必要はない

**主要な特徴:**
- HTTPのPOSTとGETリクエストを利用し、必要に応じてServer-Sent Events (SSE)を使って複数のサーバーメッセージをストリーミングできる
- 単一のMCPエンドポイント: サーバーは、POSTとGETの両方をサポートする単一のHTTPエンドポイントを提供する必要がある

#### 3つのポイント

**ポイント1: Streamable HTTP とは 「HTTP または SSE」**
- 「Streamable HTTP」ではHTTPとSSEを使い分ける
- クライアント側は `Accept: application/json, text/event-stream` または `Accept: text/event-stream` とリクエスト
- サーバー側でSSEが不要と判断したら `Content-Type: application/json` でレスポンス
- サーバー側でSSEが必要と判断したら `Content-Type: text/event-stream` でレスポンス

**ポイント2: エンドポイントパスは1つ**
- エンドポイントのパスは https://example.com/mcp のような1つのみ
- RESTのように複数のパスではない

**ポイント3: GETメソッドとPOSTメソッドを使う**
- **GETメソッド**
  - 常に Server-Sent Events（SSE）を使う
  - MCPサーバーからの通知をMCPクライアントが受け取るため、MCPクライアント側からGETリクエストを送信してSSE接続を確立しておく
- **POSTメソッド**
  - MCPクライアント側からMCPサーバーに要求を伝えたい場合はPOSTを使う
  - SSEを使ってもいいし、使わなくてもいい（SSEを使わない場合 Content-Type: application/json で応答）

#### 双方向通信の実現

**重要な疑問:** SSEは一方向チャネルです。MCPはどのように双方向通信を実現するのでしょうか？

**答え:**
- SSE長接続は1つだけで、サーバーからクライアントへのデータプッシュに使用
- クライアントからサーバーへのリクエスト送信チャネルは、通常のHTTP POSTリクエストを使用
- クライアントからサーバーへのHTTP POSTリクエストでは、命令が受信されたかどうかのフィードバックに2xx応答コードのみを使用
- すべてのデータ返信は最初に確立されたSSE長接続を通じてプッシュされる

**実装の流れ:**

1. `/sse`のURLでSSE長接続を確立した後、まずendpoint（一般的には`/message`）を返す
   - データ形式は純粋なテキストの同一ドメイン名URLの文字列

2. クライアントはPOSTリクエストをendpoint（`/message`）に送信して呼び出しリクエストを行う
   - POSTのbodyはJSON-RPC仕様に準拠し、jsonrpc、method、params、idフィールドを含む

3. `/sse`長接続で返されるイベントはJSON-RPC仕様に準拠
   - jsonrpc、result、id、error（実行エラー時）フィールドを含む

**シーケンス図のイメージ:**
- 1リクエスト・1レスポンスという訳ではなく、お互いがお互いのタイミングで会話をしていくイメージ
- どちらか片方が連続で送信しているケースがあるのが重要なポイント

#### セキュリティと堅牢性

- **DNSリバインディング攻撃を防ぐため**
  - サーバーはOriginヘッダーの検証
  - localhostへのバインド
  - 適切な認証の実装が必須または推奨

- **接続が切断された場合**
  - サーバーはSSEイベントにIDを付与することで、クライアントがLast-Event-IDヘッダーを使用してストリームを再開し、未送信のメッセージを再配信できる

- **セッション管理**
  - サーバーは初期化時にMcp-Session-IdヘッダーでセッションIDを割り当てることができる
  - クライアントは以降のリクエストでこのセッションIDを含める必要がある
  - クライアントは、不要になったセッションをHTTP DELETEリクエストで明示的に終了できる

#### 3. メッセージタイプ

- **Requests**
  - 「応答が必要」な呼び出し
  - method と params、id を持ち、サーバやクライアントに何らかの処理を要求

- **Results**
  - Requests に対する「成功応答」
  - JSON-RPC上 result フィールドを返す

- **Errors**
  - Requests が失敗した際に返るエラー情報
  - code, message, dataなどを持つ

- **Notifications**
  - 応答不要の"一方向メッセージ"
  - ログ通知や進捗通知などに使われる

### コネクションのライフサイクル

MCPはクライアントとサーバが通信する時にライフサイクルを明記しています（守らないとエラーになります）。

```
Client -[initialize request]-> Server
Client <-[initialize response]- Server
Client -[initialized notification]-> Server
Client [connection ready for use] Server
```

#### Initialization（初期化）

1. クライアントが initialize リクエストでバージョンや機能情報を送る
2. サーバが対応バージョンや機能を返す
3. クライアントが initialized 通知で応答
4. これで「初期化済み」状態となり、以降のやり取りが可能になる

#### Message Exchange（メッセージ交換）

- **Request-Response**: どちらからでもリクエストを送り、相手がレスポンスを返す
- **Notifications**: どちらからでも一方向メッセージを送れる

#### Termination（終了）

状態によって接続が終了する：
- Clean shutdown（close() など）
- ネットワーク切断
- エラー状態

### MCPのサブスクリプションモード

- resources/subscribeを使用してデータベースをサブスクライブすると、そのデータベースのすべての変更が次々とプッシュされてくる
- これはストリーム処理の一般的な使用形態に非常に似ている
- SSEはすでにサーバーからクライアントへの一方向データストリームを確立しているため、クライアントがサブスクリプションを開始すると、Flinkストリーム処理タスクを作成してMQにメッセージを送信することで、リソースのサブスクリプションを非常にネイティブに実装できる
- MCPプロトコルを使用すると、大規模言語モデルは標準的な流計算処理ノードのようになり、ストリーミングメッセージを受信したり、他のMQにメッセージを配信したりすることができる

### MCPのプログラミングモデル

MCPは、プログラミングモデルの観点から見ると、本質的にはステートフルな双方向RPC（リモートプロシージャコール）モデルであり、イベント駆動型とリクエスト-レスポンス型の特性を組み合わせています。

**MCPの主要な特徴:**

1. **ステートフルセッション**
   - 従来のステートレスなREST APIとは異なり、MCPはセッション状態を維持
   - クライアントとサーバー間に長期的な接続を確立
   - セッションには明確なライフサイクルがある

2. **双方向通信**
   - クライアントがサーバーを呼び出す（従来のRPCモード）だけでなく、サーバーもクライアントを呼び出す（逆RPCモード）ことができる
   - 例：サーバーはクライアントにAIサンプリングの実行を要求できる

3. **能力ベースの交渉**
   - 初期化段階で能力交渉を行い、利用可能な機能を動的に発見
   - 異なる実装やバージョンに適応

4. **イベント通知メカニズム**
   - 一方向通知
   - リソース変更サブスクリプションモード
   - 非同期イベント処理をサポート

5. **標準化されたインターフェース**
   - 一連の標準操作を定義
   - JSON Schemaを使用してパラメータとリターン値を定義
   - 相互運用性を促進

## 認証・認可

### 認証認可にはOAuthを使う

MCPではOAuth 2.0/2.1を使用した認証・認可を実装します。

**使用する仕様（2025/08/28時点）:**
- OAuth 2.1 IETF DRAFT (draft-ietf-oauth-v2-1-13)
- OAuth 2.0 Authorization Server Metadata (RFC8414)
- OAuth 2.0 Dynamic Client Registration Protocol (RFC7591)
- OAuth 2.0 Protected Resource Metadata (RFC9728)

### 認可の処理プロセス

1. MCPの初回起動時にDynamic Client RegistrationでClient情報を登録する
2. MCPサーバー（リソースサーバー）にMetadataを問い合わせ認可サーバーを発見する
3. ローカル上で認可サーバーを受け取るWebサーバーを起動する
4. ブラウザで認可サーバーを開き、ユーザーが認可をする
5. ローカルで立ち上げておいたWebサーバーで認可コードを受け取る
6. 受け取った認可コードと、事前に登録したクライアント情報を使ってアクセストークンを発行する

### Remote MCPの標準的な認可フロー

**ドキュメント:**

1. MCP ClientからMCP Serverにトークンなしでアクセスした際、HTTP401とともにヘッダーにResource metadata の問い合わせ先が入った状態で返ってくる（RFC9728）

2. 1で得たエンドポイントに、認可サーバーの情報を問い合わせ、取得する（RFC9728）

3. 認可サーバーに対してAuthorization Server Metadataを問い合わせ、取得する（RFC8414）

4. Authorization Server Metadataから取得した`/register` エンドポイントに、クライアント登録のリクエストを送り、認可サーバー側でクライアント登録が完了する(RFC7591)

5. Authorization Server Metadataから取得した`/authorize`エンドポイントに認可リクエストを送り、認証ページにリダイレクトする

6. 認証が完了し、アクセストークンを得た状態で元のページに遷移する

### 実際の検証ログ例

```
💡 トークンを入れない状態でMCPにリクエストをかけると、401のUnauthorized responseとresource metadataが埋め込まれたヘッダーが返ってくる
[wrangler:info] GET /sse 401 Unauthorized (7ms)

💡 resource metadataに付与されたエンドポイントに対して、具体的な認可サーバーの場所が記載されたmetadataを問い合わせ
[wrangler:info] GET /.well-known/oauth-protected-resource 404 Not Found (2ms)

💡 issuer, authorization_endpoint, token_endpointなどが含まれたmetadataを認可サーバーにリクエスト
[wrangler:info] GET /.well-known/oauth-authorization-server 200 OK (1ms)

💡 ClientをMCP側の認可サーバーに登録してもらうようにリクエスト
- URLが返却されブラウザが遷移している
- PKCEの形式に沿ってクライアント側で生成したcode_challengeを送っている
[wrangler:info] POST /register 201 Created (11ms)

```

## 実装ガイド

### サーバー実装の基本

#### 拡張性を意識してtool定義を分離する

- tool定義のインターフェイスを実装するクラスごとに個別のファイルを作成
- index.tsでtool定義をまとめてserverに登録する

#### 低レベル実装 vs 高レベルフレームワーク

**低レベル層: Server**
- @server.call_tool や @server.list_tools() などのデコレータでリクエスト種別に対応するハンドラを定義
- "どのメソッドが来たらどの関数を動かすか" を管理

**高レベルフレームワーク: FastMCP**
- SSE ルートやツール管理が自動セットアップされ、サーバー側の実装がシンプルに済む

### クライアント実装の基本

クライアントはMCPが提供する実装が比較的に少なく、基本的にSession(プロトコル層)と、stdio_client, sse_client, websocket_clientが用意されています。

**低レベル層: ClientSession**
- JSON-RPCメッセージを実際に生成し送信、サーバのレスポンスを待つ
- initialize や tools/call などのコア操作をローレベルで扱う

**トランスポート**
- 標準入出力（stdio）や SSE（HTTP経由）などを使い、JSON形式のメッセージをやり取り

## デバッグ

MCPサーバーの開発時には、適切なデバッグツールとログ機能を活用することが重要です。

### MCP Inspector

MCP Inspectorは、MCPサーバーの動作をGUIでテストするための公式ツールです。

**特徴:**
- MCPサーバーの動作を視覚的に確認できる
- ツールの実行、リソースの取得、プロンプトのテストが可能
- リアルタイムでサーバーとの通信を確認できる

**使用場面:**
- 新規MCPサーバーの開発時
- 既存サーバーの動作確認
- ツールやリソースの定義が正しく動作するかのテスト

### Logging

MCPサーバー内にログを仕込むことで、デバッグやトラブルシューティングが容易になります。

**実装方法:**

サーバーにログを仕込むには、`server.sendLoggingMessage()` メソッドを使用します。

```python
# Python の例
await server.send_logging_message(
    level="info",
    data="Processing request...",
)
```

```typescript
// TypeScript の例
await server.sendLoggingMessage({
  level: "info",
  data: "Processing request...",
});
```

**ログレベル:**
- `debug`: デバッグ情報
- `info`: 一般的な情報
- `warning`: 警告
- `error`: エラー情報

**ベストプラクティス:**
- 重要な処理の開始・終了時にログを出力
- エラー発生時には詳細な情報を記録
- 本番環境ではログレベルを適切に設定
- センシティブな情報をログに含めない

## ベストプラクティス

### 1. コンテキスト長を考慮したデータ設計

**問題:**
- 求人一覧など大量のデータを返すtoolを実行した際、コンテキスト長の制限によりリクエストが失敗するケース
- この問題は、コンテキスト長に余裕がある環境（Claude Desktopの有料版やCursorなど）では発生せず、コンテキスト長が制限されている環境（Claude Desktopの無料版など）でのみ発生

**解決策:**
- API側のページングのper_pageを縮小する
- MCP用APIでは不要なデータを除外する
- そもそも大きくなるであろう情報は含まずに返す
  - 例：GitHub MCP でも list_issues には本文などの長くなり得る情報が含まれていない
  - 1件の詳細系のToolではそのような情報を含むことができる
- MCPクライアントに返却する情報を最適化する
  - 例：Figma-Context-MCPではペイロードを最適化して返却
- シンプルにページネーション・フィルターを実装する
  - GitHub MCPの例でも、一覧系のToolにはページネーションにあたる実装がされている

### 2. Tool数の制限を考慮

**問題:**
- 公式ドキュメントに Limitations として明記されている
  - "Some MCP servers, or user's with many MCP servers active, may have many tools available for Cursor to use. Currently, Cursor will only send the first 40 tools to the Agent."

**対策:**
- 将来的に自然言語でテストを書いてもらうためにも必要だろうという当初成し遂げたかったユースケースを満たすのに十分なToolのみを提供

### 3. 素直なAPI設計

**問題:**
- 職歴更新toolで呼び出していたAPIは、バルクでのcreate・delete・updateという一般的ではないインターフェイスだった
- これはプロダクト側のUIから呼び出されていたAPI実装を踏襲したもの
- LLM側がtoolの動作を上手く把握できず、職歴の部分更新を行ってしまい、データが吹き飛ぶという問題が発生

**解決策:**
- 一般的なAPIインターフェイスに変更して、部分更新ができるようにすることで安定した呼び出しを実現

**学び:**
- LLMといえど万能ではなく、素直なAPI実装が扱いやすく安定したtool呼び出しにつながる

### 4. LLM特有の出力を考慮

**問題:**
- LLM側でtool呼び出し時のパラメーターに改行をエスケープした文字列（//n）を入れてしまい、プロダクト側の表示が崩れるケースがあった
- 仕様的なバリデーションはAPI側で行っていたが、これは想定外

**解決策:**
- MCPサーバー側でLLMの入力値をクレンジングする

## 実装時の注意点

### セキュリティ考慮事項

#### 主要なセキュリティリスク

MCPシステムには以下のようなセキュリティリスクが存在します：

1. **プロンプトインジェクション**
   - 悪意のある攻撃者がモデルのコンテキストに指示を挿入し、ユーザーが望まないことを実行させる
   - MCPの最も重要なセキュリティ脅威の一つ

2. **標準的なセキュリティリスク**
   - 従来のWebアプリケーションと同様のセキュリティリスク
   - 認証・認可の不備、データ漏洩など

3. **モデルのミス**
   - 悪意のある攻撃者によってプロンプトされなくても、モデルは間違いを犯す可能性がある
   - 例：本番データベースを削除しようとする

4. **システミックリスク**
   - AIエージェントが増え、より強力になり、人間や互いに相互作用し始めると、予期しない振る舞いが発生する可能性が高まる
   - 複数のエージェント間の相互作用による予期しない結果

#### セキュリティ対策

##### プロンプトインジェクションへの多層防御

Anthropicは「Defense-in-Depth（多層防御）」アプローチを採用しています。攻撃者が攻撃を成功させるまでに突破しなければならない複数の防御層があります。

**第1層：モデルトレーニング**

- **アプローチ**: モデルに、ユーザーの意図に反するように見える指示を無視するように教える
- **効果**: トレーニングだけで攻撃の約90%をブロックすることに成功

**第2層：分類器**

- **アプローチ**: 会話を常にスキャンし、不審なものを探し出す分類器モデルを追加
- **効果**: 第1層を突破した攻撃をさらにフィルタリング

**第3層：アプリケーション層**

- **アプローチ**:
  - ユーザーがツールの呼び出しを受け入れるか拒否するかを選択可能
  - モデルが行っていることすべてをユーザーが把握できる
- **効果**: 最終的な判断をユーザーに委ねることで、人間の監視を実現

##### その他のセキュリティ対策

1. **stdio方式の誤解への対応**
   - 「stdio方式ならローカル処理だから安全」という誤解が広まっているが、これは正しくない
   - ローカルで処理された結果は最終的にLLMプロバイダーに送信される
   - センシティブなデータの取り扱いには注意が必要

2. **DNSリバインディング攻撃対策**
   - サーバーはOriginヘッダーの検証
   - localhostへのバインド
   - 適切な認証の実装が必須または推奨

3. **視野を限定**
   - セキュリティ上、各サーバーはあくまで自分の権限内で完結
   - サーバー同士は直接データを共有しない
   - 最小権限の原則を適用

### データフローの理解

#### stdio方式のデータフロー

```
初回実行時:
1. コードをダウンロード（npm/PyPIからパッケージ取得）
   ⚠️ コードのみ（データは送信されない）
2. ローカルにキャッシュ

2回目以降:
- キャッシュから即座に実行
```

**実装言語:**
- npx: JavaScript/TypeScript製（例：@modelcontextprotocol/server-filesystem）
- uvx: Python製（例：markitdown-mcp）⚡ 10倍高速

#### HTTP方式のデータフロー

```
STEP 1: ユーザー入力
「Notionにページを作成して」
    ↓
STEP 2-3: LLMプロバイダー
- 「Notion MCPを使え」と判断
    ↓ HTTPS（インターネット経由）
STEP 4-5: Notion社のMCPサーバー
- リクエストを受信、Notionデータベースに保存
    ↓ 結果を返す
STEP 6-7: LLMプロバイダー
- Notionの処理結果を受信
```

### ライフサイクルの遵守

MCPのライフサイクルを守らないとエラーになるため、必ず以下の順序を守ること：

1. クライアントが initialize リクエストでバージョンや機能情報を送る
2. サーバーが対応バージョンや機能を返す
3. クライアントが initialized 通知で応答
4. これで「初期化済み」状態となり、以降のやり取りが可能になる
